# NATUX WORLD — передача проекта

Документ описывает текущий репозиторий: лаунчер, сайт и связанные сервисы.

## Что входит в репозиторий

| Часть | Роль |
|---|---|
| `src/`, `electron/` | React/Electron-лаунчер, установка Java/Minecraft/Forge 1.21.1, запуск, настройки, логи, обновления |
| `website/` | Next.js-сайт, аккаунты, e-mail, Yggdrasil authserver, магазин, PostgreSQL/Prisma, RCON и админ-панель |
| `website/natux-plugin/` | Серверный плагин; его сборка проверяется в Website CI |
| `.github/workflows/build.yml` | Проверки, упаковка Windows/macOS и выпуск лаунчера |
| `.github/workflows/website.yml` | Проверки сайта и плагина |

Сайт уже находится в `website/`. Старые ссылки на отдельный `minecraft-server`
не являются инструкцией по расположению актуального кода. Для передачи нужны
этот репозиторий и доступы к работающей инфраструктуре; содержимое и резервные
копии игрового сервера передаются отдельно.

## Быстрый старт для разработчика

Лаунчер, из корня репозитория:

```bash
npm ci
npm run lint
npm run typecheck
npm test
npm run dev
```

Сайт, из `website/`:

```bash
npm ci
npm run typecheck
npm test
npm run dev
```

Для сайта настройте окружение по его примеру конфигурации; нужны PostgreSQL и
сгенерированный Prisma client. Не переносите production-секреты в Git.
Сайт имеет отдельные зависимости и проверки: успешная сборка лаунчера не
проверяет `website/`.

## Бренд и адреса

- Лаунчер: `brand.config.ts` — `BRAND` и вычисляемые `BRAND_URLS`.
- Сайт: `website/src/lib/brand.ts` — `NEXT_PUBLIC_SERVER_NAME`,
  `NEXT_PUBLIC_SITE_DOMAIN`, `NEXT_PUBLIC_SERVER_IP`, `NEXT_PUBLIC_SERVER_VERSION`.
- Имя установщика, appId, иконки и GitHub-публикация: `electron-builder.yml`.

Единые конфиги уже существуют. При ребрендинге измените их согласованно перед
сборкой, а также проверьте социальные ссылки и графические ресурсы: они не все
вынесены в `BRAND`. Изменение build-time значений требует новой сборки.

## Какие проверки что подтверждают

1. `npm test`: сервисы, валидаторы и React-интеграция. UI-тесты используют настоящие
   компоненты и Zustand, но подменяют Electron bridge. Они проверяют вход, 2FA,
   прогресс установки, повтор после ошибки, отмену и состояние работающей игры.
2. `npm run build`: TypeScript, production renderer/main/preload и упаковка.
3. `npm run test:packaged`: запускает упакованное приложение с отдельным профилем,
   проверяет загрузку интерфейса входа, переход к регистрации и настоящий preload/IPC.
   На Windows по умолчанию используется `release/win-unpacked/NATUX WORLD.exe`;
   другой путь, в том числе macOS executable внутри `.app`, задайте через
   `NATUX_E2E_EXECUTABLE`.
4. `npm run test:packaged:live`: отдельная приёмочная проверка настоящего входа,
   установки, запуска Minecraft и подключения к серверу. Не входит в обычный CI.

Для live-проверки нужны выделенный подтверждённый тестовый аккаунт без 2FA,
сборка с адресами тестовой инфраструктуры, доступный сервер и его читаемый лог.
Передайте переменные окружения локально, не через аргументы командной строки:

- `NATUX_E2E_EXECUTABLE`: путь к упакованному executable.
- `NATUX_E2E_LOGIN`, `NATUX_E2E_PASSWORD`: тестовый аккаунт.
- `NATUX_E2E_USERNAME`: точный игровой ник аккаунта.
- `NATUX_E2E_SERVER_LOG`: абсолютный путь к текущему логу выделенного сервера.

Тест требует новую запись о входе этого ника в серверном логе после начала
запуска. Состояние `running` само по себе означает только запуск процесса.
Первый запуск скачивает Java и игру и может занять значительное время. Не
запускайте этот тест с обычным игровым профилем или production-аккаунтом.
Старый сервисный live-harness запускается через
`npx vitest run --config vitest.e2e.config.ts`: он проверяет старт Minecraft,
но не UI, вход в аккаунт или подключение к серверу.

## Подпись приложения и обновлений

Обычный `electron-builder.yml` сохраняет неподписанную локальную сборку.
Подготовлен отдельный профиль `config/electron-builder.signed.cjs` для выпуска
с обязательной подписью. Он включает Authenticode для Windows и Developer ID,
hardened runtime и notarization для macOS. Без обязательных параметров сборка
завершается ошибкой; отсутствие сертификата не должно давать неподписанный
артефакт в этом режиме.

В GitHub Actions установите repository variable `CODE_SIGNING_ENABLED=true` и
добавьте secrets через настройки репозитория:

| Платформа | Secrets |
|---|---|
| Windows | `WIN_CSC_LINK`, `WIN_CSC_KEY_PASSWORD` |
| macOS | `CSC_LINK`, `CSC_KEY_PASSWORD`, `MAC_SIGNING_IDENTITY`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID` |

Для CI `*_CSC_LINK`/`CSC_LINK` содержат экспортированный сертификат с закрытым
ключом в формате, поддерживаемом electron-builder (например base64 PKCS#12).
`MAC_SIGNING_IDENTITY` должен соответствовать сертификату Developer ID Application.
Windows-профиль рассчитан на доступный PFX/PKCS#12; аппаратный токен или облачный
сервис подписи потребует отдельной интеграции с выбранным провайдером.

Локальная подписанная упаковка после `npm run build:web`:

```bash
node scripts/check-code-signing.cjs --platform win
npx electron-builder --config config/electron-builder.signed.cjs --win --x64 --publish never
```

На macOS используйте `--platform mac` для проверки и `--mac --x64 --arm64`
для упаковки. Подписывайте macOS-приложение на macOS. PR-проверки продолжают
собирать неподписанные пакеты без доступа к сертификатам.

Профиль и CI-подключение не означают, что существующие релизы подписаны.
До активации и проверки первого подписанного выпуска сохраняются ограничения
первой установки. Подпись также не гарантирует отсутствие SmartScreen-предупреждений.
После выпуска проверьте `Get-AuthenticodeSignature` для Windows и `codesign`,
`spctl`, `xcrun stapler validate` для macOS на итоговых артефактах.

Ed25519-подпись `natux-update.json` проверяет канал Windows-обновлений и остаётся
отдельной от подписи executable. macOS-обновления в текущем коде остаются ручными;
одна настройка Developer ID не включает автоматическое обновление macOS.

## Передача доступов

Передавайте через защищённый менеджер паролей:

1. Права владельца этого GitHub-репозитория и GitHub Actions.
2. Резервную копию `UPDATE_SIGNING_PRIVATE_KEY` и доступ к сертификатам подписи,
   если они настроены; секреты нельзя извлечь из GitHub после сохранения.
3. Домен/DNS, хостинг сайта, PostgreSQL, почту и платёжные кабинеты.
4. Игровой сервер, RCON и authlib-injector, если используются.
5. Vercel/VPS, актуальные резервные копии БД и игровых миров.

Если ключ обновлений утрачен, нужна отдельная процедура ротации с выпуском
лаунчера, доверяющего новому ключу.

## Проверка перед передачей и выпуском

- [ ] Проверки и сборки лаунчера и сайта проходят отдельно.
- [ ] Smoke-тест упакованного приложения проходит на целевых ОС.
- [ ] Live-сценарий вход → установка → запуск → подключение проверен.
- [ ] Windows-обновление с предыдущей версии установлено успешно.
- [ ] GitHub Release содержит Setup, Portable, `.dmg`, `latest.yml`,
  `natux-update.json`, `natux-update.json.sig` и checksums.
- [ ] Для подписанного выпуска проверены подписи и macOS notarization.
- [ ] Новый владелец получил доступы и сменил чувствительные секреты.

## Как выпустить обновление

1. Внести изменения, пройти проверки и изменить версию:
   `npm version <version> --no-git-tag-version`.
2. Создать PR в `main`: CI проверяет сборку без публикации.
3. Влить PR: Build workflow публикует новую версию и update-манифест, создаёт тег.
   `workflow_dispatch` также может выпустить версию, для которой ещё нет тега.
4. Проверить загрузку, установку и обновление с предыдущей Windows-версии.

Сайт проверяется отдельным workflow; production-развёртывание выполняет
подключённый Vercel-проект. Изменения только в `website/` не выпускают лаунчер.

## Материалы для передачи

Обновите скриншоты входа, главного экрана, настроек, обновления, магазина и
админ-панели из `website/`. Не публикуйте секреты, RCON-данные, пользовательские
e-mail и реальные платёжные заказы.
